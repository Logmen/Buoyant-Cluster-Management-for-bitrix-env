# Подключаемые модули BCM

Ядро BCM управляет кластером: узлы, PXC, ProxySQL, VIP, синхронизация, копии.
Всё, что растёт вокруг него — веб-портал, экспортёры, интеграции — живёт в
**модулях**. Модуль не правит файлы ядра и не требует форка: он описывает себя
манифестом, а BCM берёт на себя раскатку по узлам, включение, хранение
параметров и пункт в меню.

## Зачем это понадобилось

Портал мониторинга (отдельный проект) к сентябрю 2026 разросся до кластерной
подсистемы: приложение на web-узлах, фронт HAProxy на балансировщиках, четыре
скрипта копий на узлах базы со своими таймерами. Ставилось это руками, поэтому:

- файлы на узлах базы разъезжались (проверено 08.09.2026: три скрипта с разницей
  в шесть часов, на одном узле новее, чем на другом);
- расширения ядра оформлялись патчами к `bin/lib/*.sh` — первый же `bcm --update`
  их затирал, и никто об этом не узнавал до следующего инцидента;
- «что вообще установлено на кластере» знал только автор расширения.

Модули закрывают ровно это: один источник файлов, одна команда раскатки, явный
список установленного в меню **16 → Модули**.

## Устройство

```
/opt/bcm-modules/<name>/        установленные модули (активные)
/opt/bcm/modules/<name>/        модули в составе самого релиза BCM (источник), если такие есть
/etc/bitrix-cluster/module-keys/ открытые ключи поставщиков (создаётся install.sh, пополняется оператором)
cluster.conf [module.<name>]    enabled = Y|N, version, свои параметры модуля
```

⚠️ Установленные модули лежат **вне** `/opt/bcm`: `bcm --update` перезаписывает
его целиком (`rsync --delete`), и модуль внутри был бы снесён первым же
обновлением ядра. Модули могут приходить откуда угодно — из отдельного
репозитория, от стороннего поставщика, из собственной сборки; каталог внутри
релиза BCM — лишь один из источников, и он не обязателен.

## Модули от сторонних поставщиков

Контракт ниже — публичный API. Модуль может разрабатываться в своём репозитории,
своей командой и продаваться отдельно от BCM; ядру достаточно манифеста.

**Совместимость.** Модуль пишется под **версию контракта** (`MODULE_API`), а не
под версию BCM: один пакет уезжает на кластеры с разными версиями ядра. Ядро
объявляет свою версию контракта в `BCM_MODULE_API` и отказывает в установке
модулю, написанному под более новый контракт. `REQUIRES_BCM` — дополнительный
нижний порог, когда модулю нужна конкретная возможность ядра.

**Пакет.** Устанавливаемый артефакт — `tar.gz`, внутри каталог модуля с
`module.conf`. Рядом кладутся `<пакет>.sha256` и, для распространения,
`<пакет>.asc` (открепленная подпись GPG).

**Проверка при установке** (`bcm_mod_install`):

| Что рядом с пакетом | Поведение |
|---|---|
| `.sha256` | сверяется обязательно; расхождение — отказ |
| `.asc` | проверяется ключами из `/etc/bitrix-cluster/module-keys/` в изолированном GPG-homedir; нет ключа или подпись не сходится — **отказ** |
| ничего | ставится с явным предупреждением (свой модуль из каталога — обычный случай разработки) |

Логика намеренно fail-closed для подписанных пакетов: подписанный артефакт,
который не удалось проверить, опаснее неподписанного — либо его подменили, либо
заказчику не передали ключ.

**Что показывается оператору.** Поля `VENDOR`, `LICENSE`, `SUPPORT` из манифеста
видны в меню 16 → «Состояние модуля»: кто выпустил, на каких условиях и куда
писать по проблемам. Для платного модуля это единственное, что отличает его в
интерфейсе от встроенных разделов, — ядро не встраивает ни лицензирование, ни
проверку ключей продукта, это дело самого модуля.

## Манифест `module.conf`

Формат KEY=VALUE, читается `source` в подоболочке.

| Ключ | Обяз. | Смысл |
|---|---|---|
| `NAME` | да | имя модуля, `[a-z0-9_-]`, совпадает с именем каталога |
| `TITLE` | да | человекочитаемое название |
| `VERSION` | да | версия модуля |
| `MODULE_API` | нет | версия контракта, под который написан модуль (по умолчанию 1) |
| `ROLES` | нет | слои для раскатки: `web lb pxc s3`. Пусто — модуль живёт только на brain-ноде |
| `REQUIRES_BCM` | нет | минимальная версия ядра; установка на более старое ядро отклоняется |
| `VENDOR` | нет | кто выпустил модуль — видно оператору |
| `LICENSE` | нет | условия использования |
| `SUPPORT` | нет | куда обращаться по проблемам модуля |
| `MENU_TITLE` | нет | если задано — у модуля появляется пункт в главном меню `bcm` |
| `MENU_SCRIPT` | нет | скрипт этого пункта, по умолчанию `menu.sh` |
| `STATE_DIRS` | нет | каталоги модуля, содержимое которых собирается на кластере, а не приезжает в пакете |
| `HOMEPAGE` | нет | где живёт исходный код |

### `STATE_DIRS` — что не принадлежит поставщику

Каталог модуля ядро копирует только целиком, с `--delete`. Если модуль собирает
часть своего состава уже на кластере (портал так делает с `payload/`: берёт
узловые скрипты из установленного на web приложения), перечислите такие каталоги
в `STATE_DIRS`. Две операции обходятся с ними по-разному, и это намеренно:

| Операция | Что происходит с `STATE_DIRS` |
|---|---|
| установка новой версии модуля | каталог **не трогается** — собранное на кластере переживает обновление модуля |
| первая установка (каталога ещё нет) | содержимое из пакета кладётся как есть |
| раскатка на узлы | каталог едет **как все**: собран он на одной ноде, а нужен на остальных |

Раскатка пустого `STATE_DIRS` не запрещена, но ядро о ней предупреждает: узлы
получат пустой каталог, а не «ничего не изменилось».

## Хуки

Исполняемые файлы в `hooks/`. Окружение:

| Переменная | Что в ней |
|---|---|
| `BCM_MODULE_NAME` | имя модуля |
| `BCM_MODULE_DIR` | каталог модуля на этом узле |
| `BCM_MODULE_ROLE` | роль узла, на котором хук выполняется (`web`, `lb`, `pxc`, `s3`) |
| `BCM_CONF_FILE` | путь к `cluster.conf` |
| `BCM_MODCFG_<ключ>` | по переменной на каждый ключ секции `[module.<name>]` (точки в имени → `_`; служебные `enabled` и `version` не передаются) |

⚠️ **Не разбирайте `cluster.conf` сами.** Параметры модуля приезжают в
`BCM_MODCFG_*`, а если хуку нужен ключ ядра — на узле есть сам BCM:

```bash
source /opt/bcm/bin/lib/bcm_config.sh
bcm_conf_get proxysql admin_password     # с учётом секции и inline-комментариев
bcm_conf_keys "module.portal"            # перечислить ключи секции
```

Самодельный `awk` по всему файлу берёт первый попавшийся ключ с таким именем,
не глядя на секцию, — а секций `[module.*]` в кластере тем больше, чем больше
модулей. На этом уже обжигались.

| Хук | Когда | Зачем |
|---|---|---|
| `install` | после раскатки каталога на узел | разложить файлы по узлу согласно роли |
| `remove` | при снятии модуля с узла — в том числе **удалённо**, со всех узлов слоёв | убрать за собой |
| `status` | по запросу меню — опрашиваются **все узлы** слоёв модуля | печатает `key=value` о состоянии на этом узле |
| `health` | таблица модулей в меню (локально, на текущей ноде) | одна строка + код 0/1 |
| `event <имя> [аргументы]` | события ядра | реакция на происходящее в кластере |

События ядра сейчас: `update.post <версия>` — ядро обновилось. Новые добавляются
в ядро явным коммитом (`bcm_mod_event`), а не патчем на узле: патч не переживёт
обновления и разъедется между узлами.

Ходить по узлам самому модулю не нужно — это делает ядро:

```bash
bcm_mod_run_remote <name> <ip> <роль> <хук> <таймаут> [аргументы]   # один хук на узле
bcm_mod_status_all <name>                                          # status со всех узлов ROLES
bcm_mod_deploy   <name>                                            # каталог + install по слоям
bcm_mod_undeploy <name>                                            # remove + удаление каталога на узлах
```

## Жизненный цикл

```
bcm → 16. Модули
  1. Установить          из состава BCM, каталога или tar.gz (проверяются манифест и REQUIRES_BCM)
  2. Включить/выключить  [module.<name>] enabled, рассылается по узлам вместе с cluster.conf
  3. Раскатать           каталог модуля → узлы слоёв из ROLES, затем hooks/install на каждом
  4. Состояние           hooks/status со ВСЕХ узлов слоёв модуля
  5. Удалить             со всех узлов (hooks/remove + каталог) либо только с этой ноды
```

При раскатке версия ядра сверяется **на каждом узле**: отставшая нода (обновление
BCM до неё не дошло) модуль не получает — иначе он молча лёг бы туда, где ему не
на что опереться.

`install.sh` раскатывает включённые модули шагом `deploy_modules` (после
`deploy_bcm`), `bcm --update` — обновляет bundled-модули из нового релиза, шлёт
`update.post` и повторяет раскатку.

## Что модулю делать нельзя

- **Править файлы ядра** (`/opt/bcm/bin`, `/opt/bcm/menu`). Не хватает точки
  расширения — её добавляют в ядро коммитом.
- **Считать, что он один на узле.** Имена в `/usr/local/sbin`, юниты systemd и
  секции конфигов — с префиксом модуля.
- **Ронять ядро.** Хуки вызываются с подавлением ошибок, но и сам модуль не
  должен оставлять узел в половинчатом состоянии: каждый шаг сообщает результат.

## Пример: модуль `portal`

Первый модуль по этому контракту — **BCM Portal**: отдельный продукт со своим
репозиторием, поставляется независимо от BCM. Показателен границей: web-часть
ставит собственный деплой портала, а модуль отвечает за то, что портал сам не
обслуживает, — узловые скрипты копий на PXC и фронт HAProxy на LB. Кода портала
модуль не хранит: `bin/refresh-payload` собирает `payload/` из установленного
приложения на кластере заказчика, и раскатка разносит его по слоям. В манифесте
этот каталог объявлен как `STATE_DIRS="payload"` — иначе установка новой версии
модуля стирала бы собранное.

Со стороны BCM он не отличается от любого другого стороннего модуля: пакет,
проверка подписи, установка, включение, раскатка.
